# 安全设计：登录失败优先告警，绝不无限重试

这份文档解释本项目最重要的设计取舍。它来自一类真实事故复盘，而不是凭空设定。

## 事故模型

第三方协议端登录态失效后，典型错误链：

```
异常关机 / 环境变化
   -> 登录票据失效
   -> 快速登录失败（"身份已失效，请重新登录"）
   -> 守护脚本自动重拉
   -> 再次快速登录失败
   -> ...无限循环...
   -> 被平台识别为异常高频行为
   -> 账号被限制（需手机端验证 / 临时冻结）
```

根因不在"登录失败"本身（这是常态），而在**失败后的自动重试死循环**。

## 四条硬规则

1. **fail-fast**：快速登录连续失败达到阈值（默认 3 次）立即熔断。
2. **告警优先**：熔断的第一时间发出 critical 告警，不等不拖。
3. **停手等待**：熔断状态下拒绝一切自动重试，只有人工确认（扫码/点按钮）才解除。
4. **状态持久化**：熔断状态写盘，进程重启后依然记得，不会从零重新死磕。

## 状态机

```
        boot
         │
         ▼
     QUICK_LOGIN ◄──────────────┐
         │ fail                  │ human_confirm()
         ▼                       │
      BACKOFF ──fail<N──> QUICK_LOGIN
         │ fail>=N
         ▼
    WAIT_MANUAL ──critical 告警──> 停手
         │
         └───────────────────────┘
```

成功路径：`QUICK_LOGIN --ok--> ONLINE`（计数清零）。
运行中被踢下线：`ONLINE -> IDLE`，由调用方重新评估，不直接无限重连。

## 退避策略

指数退避 + 抖动：`base * 2^(n-1)`，上限 `max_backoff_sec`，叠加 ±30% 抖动。
抖动后再夹一次上限，确保不突破 `max_backoff_sec`（有回归测试覆盖）。

## 告警通道

`core/notifier.py` 支持多通道并行投递，单通道失败不影响其它：

| 通道 | 用途 | 默认开启 |
|------|------|----------|
| FileChannel | 写 `logs/alerts.jsonl`，Web 面板读它显示红标 | 是 |
| ConsoleChannel | stderr，调试期可见 | 是 |
| ToastChannel | 系统托盘气泡（无控制台也能弹） | 否 |
| WebhookChannel | HTTP POST，接任意通知平台 | 否 |
| CallbackChannel | 自定义回调，接宿主事件总线 | 测试用 |

去重：相同 fingerprint 在窗口期内只告警一次，防止告警风暴。

## 部署建议

- 使用专用账号并提前养号，降低风控阈值风险。
- 固定设备、固定网络，避免频繁变更登录环境。
- 单一启动源：只保留一处自启（如 HKCU Run），面板启动走同一路径，不要多源夹心。
- 不要同时运行注入版和无头版，会抢同一登录票据。
- 已被限制时不要反复重试，停手等待恢复。

## 编码约定

框架内所有代码注释与告警文案保持中立，不含人称代词、私有项目名或内部语境。告警标题前缀通过 `GuardConfig.alert_tag` 配置，部署方填自己的名字。技术对比文档可引用第三方项目名说明取舍。
